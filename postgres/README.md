# Поиск товаров в PostgreSQL

`server-opt postgres` сравнивает две копии одного каталога.
В обеих есть primary key и обычный индекс `category_id`.
В tuned дополнительно создаётся частичный покрывающий индекс:

```sql
CREATE INDEX products_search_idx
ON products (category_id, price, id)
INCLUDE (name)
WHERE in_stock;
```

Он соответствует запросу «20 самых дешёвых доступных товаров в категории,
не дешевле заданной цены». Это стандартная возможность PostgreSQL.
Цель эксперимента — измерить пользу подходящего индекса и его цену.
Автоматического анализа и изменения пользовательских баз программа не выполняет.

Завершённый прогон на миллионе товаров: [результаты](../POSTGRES_BENCHMARK.md).

## Запуск

Нужен Linux Docker с cgroup v2. Хостовый инструмент работает на macOS и Linux,
использует Docker CLI и не требует локальных PostgreSQL или libpq.

Из корня проекта:

```sh
make
./build/server-opt postgres
```

Параметры по умолчанию:

```sh
./build/server-opt postgres --rows 1000000 --clients 8 \
  --duration 10 --repeats 4 --inserts-per-client 1000 \
  --output results/postgres.json
```

Для проверки запуска:

```sh
./build/server-opt postgres --rows 10000 --clients 2 \
  --duration 3 --repeats 2 --inserts-per-client 100 \
  --output results/postgres-smoke.json
```

Полный прогон занимает несколько минут плюс загрузку образа, создание каталога
и построение индекса. Готовые этапы записываются в JSON; неполный отчёт не содержит
`summary`. `--project-root DIR` позволяет запускать бинарник из другого каталога.

## Методика

- PostgreSQL 17 в отдельном контейнере: quota 2 CPU, RAM 1 GiB,
  `shared_buffers=256MB`, JIT выключен, параллельные планы одного запроса выключены.
- Генератор — нативный `pgbench` из того же образа, в другом контейнере:
  quota 1 CPU, RAM 256 MiB, два потока, prepared statements.
- Клиенты соединяются с PostgreSQL по приватной Docker-сети.
  Нагрузочный трафик не проходит через хостовый CLI или проброс портов.
- Каталог содержит заданное число детерминированных товаров и 100 категорий.
  Товары распределены между доступными и отсутствующими.
- Категория и минимальная цена выбираются псевдослучайно с фиксированным seed.
  В режиме фиксированного времени количество запросов различается.
- Порядок baseline/tuned чередуется; перед каждым замером чтения есть прогрев.
- 300 контрольных запросов сравниваются по отпечатку упорядоченных результатов
  до и после всех замеров чтения. Это не проверка каждого ответа pgbench.
- `EXPLAIN (ANALYZE, BUFFERS)` сохраняет реальные планы одного контрольного запроса.
- После чтения измеряются вставки: фиксированное число транзакций на клиента.
  Каждый прогон использует новую копию исходной базы; проверяется итоговое число строк.
  Прогрев перед вставками выполняет только чтение.
- Настройки `fsync`, `synchronous_commit`, `full_page_writes` записываются в отчёт.
  Они не отключаются ради скорости.
- Измеряются размер таблицы и индексов, время создания дополнительного индекса,
  средняя задержка, TPS, CPU базы на транзакцию и сырые `docker stats`.

Это замер SQL-слоя, **не времени ответа HTTP API**. Для настоящего приложения
нужно отдельно учитывать его бизнес-логику, сериализацию, сеть и пул соединений.
Латентность здесь средняя, не p95/p99. Фиксированная конкурентность не моделирует
фиксированную частоту входящих запросов. Прогрев и повторения не делают тест
проверкой предельной мощности сервера.

## Как оценивать

В `summary.read` и `summary.insert`:

- `throughput_change_percent`: положительное число означает больший TPS.
- `latency_reduction_percent`: положительное число означает меньшую среднюю задержку.
- Для обоих профилей есть медианы, диапазон TPS и число ошибок.
- `server_cpu_us_per_transaction` включает фоновую работу базы и команды измерения,
  поэтому это приближённая стоимость, не чистое время выполнения SQL.

`extra_relation_bytes` и `relation_size_increase_percent` показывают цену на диске.
Это размеры отношений PostgreSQL, а не RAM, весь Docker-том или WAL.
Индекс также может замедлить вставки и обновления; обновления/удаления здесь не тестируются.
Выигрыш поиска не превращается автоматически в такой же выигрыш всего приложения.
Энергия не измеряется.

## Изоляция и очистка

Тест создаёт новые контейнеры, приватную internal-сеть и отдельный том только
с синтетическими данными. PostgreSQL-порт на хост не публикуется.
В этом изолированном стенде используется trust-аутентификация; такой режим
не следует переносить на пользовательскую или публично доступную базу.

По завершении и обычному Ctrl+C контейнеры, сеть и том удаляются.
Образ `server-opt-postgres:local` остаётся. При SIGKILL/аварии хоста очистка
может не выполниться. Собственные ресурсы стенда помечены
`app=server-opt-postgres`; чужие базы и Docker-ресурсы программа не изменяет.
