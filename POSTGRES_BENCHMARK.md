# Поиск по миллиону товаров: результат 15 октября 2026

**В этом SQL-сценарии добавление индекса увеличило пропускную способность
с 221 до 66 112 запросов/с: примерно в 299 раз (+29 763%).**
Средняя задержка снизилась с 36,12 до 0,1165 мс (−99,68%).
Вставки стали медленнее на 3,41%, размер таблицы вместе с индексами вырос на 58,02%.

Изменение использует стандартный индекс PostgreSQL.
Server Opt создаёт изолированный стенд, проверяет результаты и измеряет эффект.
Это не заявление о таком же ускорении произвольной базы, всей ОС или HTTP API.

## Что сравнивали

Миллион детерминированных товаров, 100 категорий, цены от 0 до 999,99,
доступные и отсутствующие товары в каждой категории. Запрос:

```sql
SELECT id, name, price
FROM products
WHERE category_id = :category AND in_stock AND price >= :min_price
ORDER BY price, id
LIMIT 20;
```

Оба профиля содержат primary key и индекс категории. В tuned добавлен:

```sql
CREATE INDEX products_search_idx
ON products (category_id, price, id)
INCLUDE (name)
WHERE in_stock;
```

Данные tuned скопированы из baseline. Бизнес-результат запроса не изменён.
Планировщик выбирал планы самостоятельно; принудительное включение
конкретного индекса или отключение sequential scan не применялись.

## Окружение и нагрузка

- Linux VM Lima 2.2.0 на Apple Silicon: Ubuntu 26.04, 4 vCPU, 4 GiB RAM.
- PostgreSQL 17.11 в образе на Debian Bookworm; Docker 29.9.1, cgroup v2.
- База: quota 2 CPU, RAM 1 GiB, shared buffers 256 MiB.
- JIT и параллельное исполнение одного запроса выключены одинаково в обоих профилях.
- Генератор: нативный pgbench в отдельном контейнере, quota 1 CPU, 256 MiB RAM,
  два потока, восемь клиентов, prepared statements.
- Трафик между контейнерами по внутренней сети, без проброса через macOS.
- Чтение: 15 секунд на замер, четыре повтора каждого профиля.
- Вставки: по 10 000 транзакций на каждого из восьми клиентов,
  четыре повтора каждого профиля; каждый раз свежая копия исходной базы.
- Порядок профилей чередуется. Перед каждым замером — две секунды чтения для прогрева.
- `fsync`, `synchronous_commit`, `full_page_writes` включены.

## Почему выигрыш большой

Сохранённый `EXPLAIN (ANALYZE, BUFFERS)` для одной категории и минимальной цены 500:

- Baseline: bitmap scan нашёл 10 000 строк категории, отфильтровал 6000,
  затем отсортировал подходящие строки для выбора первых двадцати.
  Верхний узел плана показывает 10 017 обращений к страницам shared buffers.
- Tuned: index-only scan получил нужные двадцать строк в правильном порядке.
  Четыре обращения к страницам shared buffers, ноль обращений к таблице
  (`Heap Fetches: 0`). Отдельная сортировка не нужна.

Это устранение лишнего чтения и сортировки в конкретном запросе.
При другой фильтрации, сортировке, выборе колонок или частых изменениях таблицы
такой индекс может дать другой результат. После изменений таблицы index-only scan
может потребовать обращений к heap до следующего VACUUM.

## Проверки и ограничения

Все 16 измерений имеют `measurement_valid: true`; ошибок запросов и сбора метрик нет.
Отпечатки результатов 300 контрольных запросов совпали до и после чтения.
После каждого теста вставок число строк равно 1 080 000.
Проверяются контрольные запросы; pgbench не сравнивает содержимое каждого ответа.

В активных выборках сервер использовал примерно два CPU, а клиент tuned —
около 68–75% одного CPU. Прежний однопоточный HTTP-генератор здесь не используется.
Это всё равно тест на общей VM и синтетических данных, не предельная мощность
физического сервера.

CPU на запрос рассчитан по cgroup базы и включает фоновую работу и команды
учёта. Это не энергопотребление. Размер на диске относится к таблице и индексам,
не RAM, всему тому или WAL. Средняя задержка не характеризует p95/p99.
Обновления, удаления, смешанная нагрузка, холодный кеш и полное HTTP API
в этот эксперимент не входили.

Большой выигрыш относится к подходящему запросу, у которого раньше не было
такого составного индекса. На уже правильно проиндексированной базе его
повторное добавление не даст этого эффекта.

## Повторение и артефакты

```sh
make
./build/server-opt postgres --rows 1000000 --clients 8 \
  --duration 15 --repeats 4 --inserts-per-client 10000 \
  --output results/postgres-million.json
```

- `results/postgres-million.json` — полный отчёт, исходный SQL, параметры,
  ID образа, планы, результаты всех повторений и сырые метрики.
- `results/postgres-million-summary.json` — сокращённый отчёт.
- `results/postgres-million.log` — порядок запусков и прогресс pgbench.
- `results/postgres-smoke.json` — предыдущая проверка на 10 000 строках.
- `results/postgres-million-instrumentation-error.json` — первый большой прогон:
  два сбоя получения Docker stats, `measurement_valid: false`.
  Он сохранён для прозрачности и **не использован** в таблице выше.

Для исправления сборщик метрик запускается после старта клиента, а не пока
контейнер находится в состоянии `created`. Полный эксперимент повторён после исправления.

Контейнеры, сеть и том с тестовыми данными удалены. Образ оставлен для повторения.
VM после завершения проверок остановлена.
