# Измерение 15 октября 2026

**В проверенной конфигурации один worker Nginx использовал на 40,93% меньше
памяти контейнера — экономия 1,986 МиБ. Прирост пропускной способности
не подтверждён: разница медиан +0,47% меньше наблюдаемого разброса прогонов.**

Это результат изменения штатной настройки Nginx `worker_processes auto` на `1`.
Программа Server Opt запускает сравнение и собирает результаты; запуск аудита
или генератора нагрузки сам по себе не оптимизирует приложения.

## Условия

- Apple Silicon, Linux VM через Lima 2.2.0 / Apple Virtualization.
- VM: Ubuntu 26.04 LTS, aarch64, 4 vCPU, 4 GiB RAM.
- Docker Engine 29.9.1, cgroup v2.
- Оба контейнера: Ubuntu 24.04, Nginx `1.24.0-2ubuntu7.18`,
  quota 1 CPU, лимит RAM 256 MiB.
- Baseline: четыре workers и master; tuned: один worker и master.
- Один и тот же небольшой JSON, HTTP/1.1 keep-alive, без TLS и базы данных.
- 32 одновременно выполняемых запроса, 15 секунд на замер,
  шесть повторений каждого профиля, прогрев перед каждым замером.
- Порядок: baseline/tuned, затем tuned/baseline, с чередованием по раундам.
- Генератор C++17 собран с `-O2`, GCC 15.2, libcurl 8.18.0.
  Генератор работал внутри Linux VM, без проброса нагрузочного трафика через macOS.
- Все ответы проверялись по HTTP-статусу и точному содержимому.

ID общего образа:
`sha256:2f1c6a9a6a70bd14fadf5feb460670673d69c283e2f012be1fac7912784b9fef`.

## Результат

В таблице — медианы шести прогонов каждого профиля.

| Метрика | auto / 4 workers | 1 worker | Изменение |
|---|---:|---:|---:|
| Память контейнера под нагрузкой | 4,852 МиБ | 2,866 МиБ | −40,93% |
| Успешные запросы/с | 75 803 | 76 159 | +0,47% |
| p95 успешного запроса | 0,4415 мс | 0,4065 мс | −7,93% |
| Ошибки во всех замерах | 0 | 0 | Без изменений |

Снижение p95 в абсолютном выражении — 0,035 мс. Это медиана p95 отдельных
прогонов, вычисленных по выборке успешных запросов, а не p95 всех запросов вместе.

Разброс между отдельными прогонами:

| Метрика | auto / 4 workers | 1 worker |
|---|---:|---:|
| Минимум–максимум запросов/с | 70 585–76 503 | 71 614–76 662 |
| Минимум–максимум памяти | 4,777–4,936 МиБ | 2,762–2,918 МиБ |

В каждом раунде память tuned была ниже baseline. Направление изменения
пропускной способности менялось: в пятом раунде tuned был медленнее.
Статистический тест значимости не выполнялся.

## Что можно утверждать

В этом сценарии ограничение числа рабочих процессов уменьшило расход RAM
контейнера примерно на 2 МиБ. Это воспроизводилось во всех шести парах замеров.
Память измерялась через `docker stats`, с исключением части кеша и округлением.
Процент относится к памяти небольшого контейнера Nginx, не всей VM,
операционной системы или приложения с базой данных.

Генератор использовал около 94% одного CPU. Его собственная производительность
может ограничивать измеренную пропускную способность. Максимальная мощность
сервера и увеличение числа поддерживаемых пользователей этим тестом не определены.
Для этого нужны независимый более мощный генератор и нагрузка реального приложения.

На многопроцессорном сервере без quota один worker может ухудшить результат.
Если `auto` уже выбирает один worker, изменения конфигурации вообще нет.
Проценты нельзя распространять на все серверы и пользователей.
Энергия и денежная экономия не измерялись.

## Артефакты и повторение

- `results/comparison-c32.json` — полный отчёт, все 12 замеров и сырые метрики.
- `results/comparison-summary.json` — агрегаты и диапазоны.
- `results/comparison-c32.log` — порядок запуска.
- `results/linux-build-test.log` — сборка в Linux и 17 прошедших тестов.

Исходный запуск с неполной колонкой `docker top` завершился ошибкой сбора
числа процессов. Команда исправлена на `ps -eo pid,comm`, затем эксперимент
запущен заново целиком. Таблица выше использует только этот полный прогон.

В подготовленной VM запускалась команда:

```sh
DOCKER_BUILDKIT=0 /home/lima.guest/server_opt/build/server-opt experiment \
  --project-root /home/lima.guest/server_opt \
  --duration 15 --repeats 6 --concurrency 32 \
  --output /home/lima.guest/server_opt/results/comparison-c32.json
```

`DOCKER_BUILDKIT=0` использовался для повторного использования ранее собранного
образа через legacy builder. На другом сервере можно использовать обычный
`./build/server-opt experiment` с теми же параметрами нагрузки.

После замеров VM остановлена. Локальные инструменты находятся в `.tools/`,
данные VM — в `.lima/`; эти каталоги исключены из Git. Образ загрузки Lima также
кешируется в `~/Library/Caches/lima`. Для повторного запуска этой VM из корня проекта:

```sh
LIMA_HOME="$PWD/.lima" .tools/bin/limactl start server-opt
```
