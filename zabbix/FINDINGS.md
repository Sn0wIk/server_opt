# Zabbix — реальное приложение, находки

Стенд: Lima VM (Ubuntu ARM64, 4 vCPU, 4 GiB), Docker:
`postgres:15-alpine` + `zabbix/zabbix-server-pgsql:alpine-7.0-latest` +
`zabbix-web-nginx-pgsql` + `zabbix-agent`. `pg_stat_statements` включён.

Нагрузка: хост `load-host` с 10 trapper-метриками, ~3 мин потока через
`zabbix_sender` (пакетами по 200 значений), параллельные чтения через JSON-RPC API
(`history.get`, `item.get`). В `history_float` записано ~2,7k строк.

## Топ по суммарному времени (results/analyze-zabbix.json)

| Rank | Calls | Среднее | Всего | Запрос |
|---:|---:|---:|---:|---|
| 1 | 4 | **2070 мс** | **8,28 с (77%)** | `SELECT` триггеров через `IN (SELECT DISTINCT ... FROM triggers tg, functions f, items i, item_discovery id ...)` |
| 2–10 | 1 | 96–449 мс | ~1,9 с суммарно | Огромные multi-row `INSERT INTO items / item_tag / widget_field / functions / triggers ...` — это разовая загрузка шаблонов при старте |

## Находки

1. **Запрос триггеров — 2 секунды на вызов.** Это `configuration sync` Zabbix:
   выборка триггеров через 4-табличный implicit join (`triggers`, `functions`,
   `items`, `item_discovery`). Известный тяжёлый запрос Zabbix при загрузке
   конфигурации/после изменений. Анализатор пометил его флагом
   `implicit_comma_join_check_plan`. На маленькой базе 2 с — заметно; на
   реальных инсталляциях с десятками тысяч триггеров это одна из причин
   «тормозов» веб-морды и sync-ов.

2. **Schema import доминирует в статистике свежей установки.** Большая часть
   «тяжести» — разовые вставки шаблонов. Вывод для инструмента: статистику
   надо смотреть **после устаканивания нагрузки** или сбрасывать
   `pg_stat_statements_reset()` перед замером, иначе bootstrap шумит.

3. **Текст запроса может быть мегабайтами.** Одна запись
   `pg_stat_statements` содержала ~3,2 МБ текста (много-строковый INSERT при
   импорте схемы). В SQL теперь `left(..., 400)` — без этого вывод раздувается
   сверх разумного и разбор падает по лимиту вывода.

## Эксперимент: housekeeper DELETE vs партиции (измерено)

Залито **10 000 000 строк** в `history`, размазанных по 30 дням (таблица 1094 MB).
Симулирована очистка ретенции: удаление ~3,1 млн строк старше 20 дней.

| Подход | Удалено | Время | Место после | Дополнительно |
|---|---:|---:|---:|---|
| `DELETE WHERE clock < ...` (стоковый housekeeper) | 3 088 445 | **2 994 мс** | таблица осталась **1094 MB** — место не вернулось ОС | ~3,1 млн dead tuples, нужен VACUUM; рост WAL |
| `DROP TABLE` 10 партиций | 2 932 261 | **~50 мс** (0,37 с с запуском psql) | **786 MB** — ~308 MB освобождено сразу | dead tuples = 0, WAL минимальный |

Итого на 10M строк: очистка **~60× быстрее** + реальное возвращение диска.
DELETE масштабируется линейно от удаляемых строк и борется за ресурс с живой
нагрузкой; DROP PARTITION почти константен. На 300M+ строках разница превращается
в минуты/часы против миллисекунд — это задокументированная боль Zabbix-инсталляций.

Порог честности: на 10M строк DELETE ещё терпим (3 с). Драма начинается на
десятках–сотнях миллионов строк и при параллельной нагрузке: bloat, WAL-шторм,
лаги реплики, блокировки.

## Масштаб 100M строк (измерено)

Залито **100 001 609 строк** в `history` (10 GB, 30 дней). Очистка ~33 млн
старых строк (старше 20 дней), параллельно шли чтения `SELECT ... WHERE
itemid=? AND clock > now-1d` (как у dashboards/history.get).

| Метрика | DELETE (стоковый housekeeper) | Партиции (DROP) |
|---|---:|---:|
| Время удаления | **31 527 мс** (seq scan 100M) | **~3 с** wall / ~сотни мс в БД |
| VACUUM после | **+41,9 с** (33M dead tuples) | не нужен |
| Итого тяжёлой работы | **~74 с** | **~3 с** |
| Диск после очистки | 10 GB — **не вернулся ОС** | освобождено мгновенно |
| p50 чтения во время очистки | 182 мс | 57 мс |
| p95 чтения во время очистки | 211 мс | 70 мс |

**Бонус:** чтения по партиционной таблице быстрее сами по себе — p50 **57 мс
против 180 мс** на монолите (~3× быстрее), потому что индекс каждой партиции
мельче. Это ускоряет дашборды и `history.get` постоянно, не только при очистке.

Честные оговорки: разница объёмов — DELETE удалил 32,9M строк, DROP — ~15,8M
(граничная партиция остаётся до следующего дня, так делают в реальных схемах).
На чтениях во время DELETE деградации почти не видно — VM с 4 vCPU и данными
в RAM; на реальном диске/реплике картина хуже (WAL-шторм, IO, лаги).

### Деньги (прозрачная проекция с измеренной базой)

- Housekeeping: ~74 с тяжёлой работы vs ~3 с → ~25× меньше CPU/IO на очистку.
  На деплое с десятками NVPS housekeeper идёт часами ежедневно.
- Диск: мгновенный возврат места vs накопление bloat — типично −30–50% объёма
  исторических таблиц.
- Чтения: ~3× быстрее на горячем пути.

## Вывод для продукта

- Флаг `implicit_comma_join_check_plan` нужен: реальные тяжёлые запросы часто
  прячут join в подзапросе `IN (SELECT ... FROM a, b, c)`, а не в явном `JOIN`.
- Нужен режим `analyze --reset` (или отдельная команда сброса статистики)
  перед нагрузочным окном, чтобы чистить bootstrap-шум.
- Здесь `pg_stat_statements` уже показал реальный болезненный запрос без
  каких-либо индексов с нашей стороны — это и есть ценность инструмента.
